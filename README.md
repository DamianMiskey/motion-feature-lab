# Motion Feature Lab

A hands-on tour of **GSAP**, **Rive** and **Three.js**. Each page demos one technique live, explains it, and shows the code behind it. A sibling of the [Vercel Feature Lab](https://vercel.djmiskey.com) and the [Cloudflare Feature Lab](https://lab.djmiskey.com), built to the same pattern.

**Stack:** Next.js 16 (App Router, TypeScript, Cache Components) · Tailwind CSS v4 · GSAP 3 with `@gsap/react` · Rive (`@rive-app/react-canvas`) · Three.js with react-three-fiber and drei · live at **https://motion.djmiskey.com** (`motion-feature-lab.vercel.app` redirects there with a 308).

## Run it

```bash
npm install
npm run dev        # http://localhost:3000 (copies the Rive runtime into public/ first)
```

Production build locally: `npm run build && npm start`.

## Checks

```bash
npm run lint
npm run typecheck
npm test           # Vitest: feature registry, robots.txt and sitemap, Rive colour conversion, game levels
npm run build
npm run e2e        # Playwright against the build (starts `npm start` on :3100)
BASE_URL=https://motion.djmiskey.com npm run e2e   # …or against any deployment
```

CI (`.github/workflows/ci.yml`) runs all five on every pull request.

**End-to-end tests** (`e2e/`, Playwright): `pages.spec` loads every page on desktop and a Pixel 7, mounts every lazy demo, and fails on any uncaught exception, console error (CSP blocks included) or sideways overflow; `headers.spec` checks the security headers and that `'wasm-unsafe-eval'` is allowed exactly where `src/lib/wasm-pages.ts` says; `a11y.spec` runs axe (WCAG 2.2 A/AA) on every page in light and dark mode; `interactions.spec` drags, throws, scrolls the wheel, presses keys and plays a game round. Locally they use the installed Microsoft Edge (`channel: "msedge"`, no browser download); CI installs Chromium and renders WebGL with SwiftShader. Two traps the suite works around: on an emulated phone the layout viewport grows to fit too-wide content, so overflow is measured against the device width, not `innerWidth`; and WebAssembly errors arrive after a demo's chunk has loaded, so `waitForDemos` waits for the network to go idle. On CI (2 cores, WebGL in software) the suite runs one worker at a time: two 3D pages at once pushed frames past half a second, where GSAP's lag smoothing stretches every animation (Marble Maze's 3.6 s countdown never finished, and axe caught panels mid-fade as contrast failures). Tests therefore wait for state, not time: Marble exposes `data-state`, and the accessibility scan waits until inline opacities stop changing. The suite was checked by breaking things on purpose (the carousel overflow, a missing CSP entry): both fail it.

## Layout

| Path | What lives there |
|------|------------------|
| `src/lib/features.ts` | Registry of all pages; drives the nav, the home page and the sitemap |
| `src/app/<slug>/page.tsx` | One folder per page; demos are Client Components next to it, and `lazy.tsx` wraps the heavy ones |
| `src/components/motion/` | `MotionProvider` (reduced motion, FPS setting), `useInView`, `FpsMeter`, `MotionControls` |
| `src/components/` | `FeaturePage`, `Demo`, `CodePeek`, `Nav`, and `ui.tsx` (`Button`, `Stage`, `cx`) |
| `src/app/globals.css` | Tailwind import, light/dark colour tokens mapped into `@theme`, element defaults |
| `public/rive/` | `.riv` files (see `CREDITS.md`) and the Rive runtime, copied in at build time |
| `next.config.ts` | Cache Components, security headers, CSP |

**Adding a page:** create `src/app/<slug>/page.tsx` using `FeaturePage` and add it to `features.ts` with `ready: true` (the `[slug]` placeholder route for unbuilt pages was removed once everything was built; bring it back if you add `ready: false` entries). Wrap anything that imports Three.js or Rive in a `lazy.tsx` (`next/dynamic` with `ssr: false` inside `WhenVisible`). Rive pages must be named `rive-*` (a test enforces it), because only those paths get WebAssembly in the CSP.

## Notes

- **Styling** is Tailwind CSS v4 (CSS-first: no `tailwind.config`, just `@import "tailwindcss"` and `@theme` in `globals.css`, plus `postcss.config.mjs`). Colour tokens are CSS variables switched by `prefers-color-scheme`, exposed as theme colours (`bg-surface`, `text-muted`, `border-line`, `bg-accent`…), so dark mode needs no `dark:` variants. Repeated pieces are small components in `ui.tsx` rather than global classes. Some class names in the demos (`box`, `scrub-bar`, `lines-demo`, `morph`…) aren't styling: they're the hooks GSAP selects.
- **Motion settings**: `MotionProvider` follows the system's `prefers-reduced-motion` by default; the sidebar can override it (Reduce / Full) and toggle an FPS meter, both remembered in `localStorage`. Demos read `useMotion().reduced` and swap large movement for fades and skip autoplay; they also pause off screen with `useInView` (Rive uses its own IntersectionObserver option, Three.js switches `frameloop` to `"demand"`). Plain CSS can use `[data-motion="reduce"]` on `<html>`.
- **GSAP** is free for all uses, including the formerly paid plugins (ScrollTrigger, SplitText, MorphSVG, DrawSVG, Flip), all in the `gsap` package. The only restriction is building a no-code animation tool that competes with Webflow. Animations live in `useGSAP()`, which scopes selectors and reverts everything on unmount.
- **GSAP plugins** are registered once in `src/lib/gsap.ts` (import from there, in Client Components only). Animations started from event handlers go through `contextSafe` so `useGSAP` cleans them up. **ScrollTrigger** demos reveal, scrub and pin (with `invalidateOnRefresh` so distances are re-measured on resize). **SplitText** (rewritten in 3.13) uses `mask: "lines"`, `autoSplit` with `onSplit` returning the animation (re-split on resize, same progress), and `aria: "auto"` so screen readers get the original sentence as an `aria-label` and the fragments are `aria-hidden`. **Flip** records positions with `getState()` before a React state change and runs `Flip.from()` after the new layout renders. With reduced motion: no splitting, no pinning or scrubbing, drawings complete, morphs and layout changes instant.
- **Interaction** (phase 7): Draggable, InertiaPlugin, Observer and MotionPathPlugin are registered in the demo files that use them, not in `src/lib/gsap.ts`, and those demos load through `lazy.tsx` like the Three.js and Rive ones, so no other page downloads or prefetches them. Draggable's `snap` only applies to a throw, so with reduced motion (inertia off) the demos snap in `onDragEnd`; Draggables are killed explicitly in the `useGSAP` cleanup. Handlers that start tweens call `contextSafe(() => …)()` at event time: wrapping a function that reads refs during render trips React's `react-hooks/refs` lint rule. Observer never blocks the page by itself: a separate non-passive wheel listener swallows only wheel movements that change the slide. Pointer effects run inside `gsap.matchMedia("(hover: hover) and (pointer: fine)")`. Rive's **events** are deprecated in favour of data binding, so the Rive input page uses state machine listeners instead: focus, key and text listeners and text fields, with `tabIndex: 0` on the canvas, `enableRiveAssetCDN: false`, and the experimental `semanticsMode` for a hidden accessible DOM mirror.
- **Advanced 3D** (phase 8): `@react-three/postprocessing` effects are conditional children of `<EffectComposer>`; only colours pushed past 1.0 (`toneMapped={false}`) bloom. Instancing reads `gl.info.render` for live draw-call and triangle counts. **Rapier** (`@react-three/rapier`) embeds its WebAssembly in a ~835 KB (gzip) chunk, loaded only by its lazy demo; WebAssembly pages are listed in `src/lib/wasm-pages.ts`, which `next.config.ts` turns into the CSP rule and a test checks against every page that imports Rive or Rapier. With reduced motion the physics world stays paused until the visitor presses Run. **WebGPU**: `WebGPURenderer` from `three/webgpu` is created by an async factory in R3F's `gl` prop (`await renderer.init()`), falls back to WebGL 2 by itself, and the material is TSL (`three/tsl`) node code; the per-frame uniform write carries one narrow `react-hooks/immutability` exemption. `three/webgpu` is a ~190 KB (gzip) separate build only that page loads.
- **Capstone** (phase 9, `/game`): `levels.ts` holds the layouts and scoring as plain data (unit-tested: no overlaps, everything on the platform). `GameWorld.tsx` is the Rapier world; blocks report their own fall once, with the point projected to the screen for the "+100" pop, and a throw is a ray from the camera through the crosshair (`Raycaster.setFromCamera`) with `ccd` balls. `Game.tsx` is the shell: React state for the round, refs mirrored for timers and physics callbacks, a GSAP-tweened object the camera follows, widened field of view on portrait screens, and keyboard aiming (arrows + Space) on a focusable `role="application"` layer. `rating.riv` predates data binding, so its stars use the deprecated state machine input (`useStateMachineInput`, warning suppressed). The physics world is a `React.lazy` chunk so the shell and a GSAP loader show while Rapier downloads; Rive's runtime is about as big as Rapier's (~820 KB gzip), so it's warmed with `RuntimeLoader.awaitInstance()` only after the physics is ready, instead of being used as the loader. Best total lives in `localStorage` (wrapped in try/catch).
- **Marble Maze** (phase 10, `/marble`): the board never moves in the physics; `world.gravity` is tilted each frame and the camera rotates by the inverse, which looks identical to a tilting board and avoids a rotating kinematic body. The floor is a single `TrimeshCollider` over every non-hole cell (shared vertices, so no ghost collisions at tile seams), walls are merged into horizontal runs, the goal is a sensor collider. `tilt.ts` merges three inputs: DeviceOrientation (iOS needs `requestPermission()` inside a tap), arrow keys/WASD on the focused board, and drag-as-joystick. Phone tilt doesn't use beta/gamma directly: Euler angles break down in landscape (gamma hits its ±90° limit, beta flips), so `upOnScreen()` turns them into the world's up direction in screen coordinates (smooth however the phone is held), and `tiltFrom()` measures it against the pose at "Play", recalibrating when the screen rotates. Both are pure and unit-tested in all four orientations. The marble's position is mirrored to `data-ball` on the board layer, which the end-to-end autopilot reads to steer along the level's shortest path. Per-frame mutable state (Rapier's world, scratch vectors) lives in refs to satisfy React's immutability lint. `CodePeek` code boxes are now keyboard-focusable (they failed axe's scrollable-region rule once expanded).
- **Stacker** (phase 11, `/stacker`): built light for phones: no Rapier, no Rive, so the page loads no WebAssembly. `stack.ts` holds the rules as pure functions (drop → perfect / cut + falling chunk / miss, growth after a streak, a ping-pong slide, speed by height). The game owns the live state in a ref and passes the scene a `step(dt)` callback, so the scene only reads it (React's lint forbids mutating a ref received as a prop); React state changes only on a drop, and everything a drop records is copied out of the live game *before* the state updates are scheduled: updater functions run later, after the game has moved on to the next level, and reading `g.level` inside one placed every slab a level too high, inside the next sliding slab (slabs seemed to pass through each other, with z-fighting flicker). `data-top` on the game exposes the top slab's level, and the e2e test checks it equals the score. Cut-off pieces tumble with a few lines of hand-written gravity. Three.js's colour parser only accepts the comma form `hsl(h, s%, l%)`: the space-separated CSS form silently renders white. The sliding slab's offset is mirrored to `data-offset` for the autopilot test, which must wait for each new slab's first frame (the attribute still shows the previous slab's offset until then).
- **Starfield Runner** (phase 12, `/runner`): `field.ts` holds the rules (seeded mulberry32 generator, spawning, hit / near-miss classification as a rock crosses the ship's plane, speed curve), unit-tested. The rock count was tuned by simulation: at 260 a simple dodging autopilot survived a median 4 s, at 90 about 15 s; a ship that never moves always lasts about 2 s. Rocks that pass are recycled to the far end (object pooling), so nothing is allocated while flying; frame time is capped at 50 ms so a stalled tab doesn't teleport the field. Scenery rocks outside the corridor fill the view (without them the corridor bunches into a ball in the middle distance). The game owns state in a ref and hands the scene `step(dt)`, as in Stacker; HUD numbers are written straight to the DOM. Steering reuses `marble/tilt.ts`.
- **Leaderboards** (`src/components/Leaderboard.tsx`): all four games post a finished run to the [API lab](https://api.djmiskey.com/idempotency) (`NEXT_PUBLIC_SCORES_API`, default `https://api.djmiskey.com`, also allowed in the CSP's `connect-src`). Players enter three initials (A–Z, remembered in localStorage); Marble Maze posts its total time in milliseconds (lower is better), Tower Toppler its total after all levels. Each run gets one `Idempotency-Key`, reused when a network error, 5xx or 409 is retried (after 1 s, then 2 s) or the player presses Submit again, so one run can't be counted twice. The top five update live over Server-Sent Events, only on the end-of-game screen and for at most two minutes, so visitors don't hold a server stream open. End screens are centred with `m-auto` in a scrollable overlay, so a tall panel on a phone scrolls instead of being cut off. Tests never touch the real boards: `e2e/fixtures.ts` replaces the API with an in-memory fake that records each submission.
- **Real user monitoring** (`src/instrumentation-client.ts`, `src/lib/faro*.ts`): [Grafana Faro](https://grafana.com/oss/faro/) reports web vitals (LCP, INP, CLS, FCP, TTFB), JavaScript errors, console warnings/errors, page events and request timings from visitors' browsers to Grafana Cloud Frontend Observability (app `motion-lab`, Free plan: 50,000 sessions a month); the [Observability lab](https://obs.djmiskey.com/real-users) shows them. Only at `motion.djmiskey.com` (local, previews and tests send nothing), and only after the `load` event when the browser is idle: `instrumentation-client.ts` runs before hydration but just schedules a dynamic `import()` of the SDK, so it's a separate chunk and can't slow the page down (checked: first report ~330 ms after load, no Faro script in the initial HTML). Sessions are per tab (`sessionStorage`), no cookies or user ids; session replay is off. Requests to `api.djmiskey.com` get a `traceparent` (`TracingInstrumentation`, `propagateTraceHeaderCorsUrls`), so a leaderboard call's trace continues into the API lab. The collector URL isn't secret (every browser sees it; Grafana accepts it only from this origin) and is allowed in `connect-src`. The home page says what's collected.
- **Rive**: the runtime is WebAssembly. Rive loads it from the jsDelivr CDN by default; `src/lib/rive-runtime.ts` points it at `/rive/rive.wasm` on this site and turns the CDN fallback off, and `scripts/copy-rive-wasm.mjs` copies the file from `node_modules` before `dev` and `build`. Only `rive-*` pages get `'wasm-unsafe-eval'` in their CSP. State machine *inputs* are deprecated in favour of **data binding**: `/rive-data-binding` binds a view model instance (`useViewModel` + `useViewModelInstance` with `autoBind: false`) and uses the typed hooks for strings, enums, colours (ARGB numbers; `src/lib/rive-color.ts` converts), numbers and triggers, both ways: it reads a colour the file computes and counts a trigger fired inside the file. `/rive-layouts` switches `fit`/`alignment` on the running instance (`rive.layout = …`, one narrow lint exemption). `Fit.Layout` resizes the artboard itself and that size sticks, so switching to another fit calls `resetArtboardSize()` and switching back calls `resizeDrawingSurfaceToCanvas()`. Files exported from Rive's free plan carry a Rive splash screen; the examples here are MIT-licensed files from Rive's own repositories.
- **Three.js** runs through react-three-fiber 9 (React 19). Every scene uses `components/three/ThreeCanvas.tsx`: a no-WebGL `fallback`, and `frameloop="demand"` when motion is reduced or the canvas is off screen (children get `animate` to know whether to move things). **Models**: `useGLTF(path, false, false)` turns off Draco/Meshopt so drei never fetches decoders from Google's CDN; animations play through `useAnimations`, paused with `setEffectiveTimeScale(0)`. The Fox model is CC BY 4.0 (credited on the page and in `public/models/CREDITS.md`); DamagedHelmet was skipped because part of it is CC BY-NC. **Materials** are lit by drei `<Environment>` built from `<Lightformer>` panels, so no HDR file or CDN preset is loaded. **Shaders**: `waveMaterial.ts` defines GLSL with drei `shaderMaterial()` and registers it with `extend()`; it's imported for that side effect explicitly, because a type-only import gets dropped by the build.
- **Hosting**: Vercel project `motion-feature-lab` (team two-seats), connected to GitHub, so every PR gets a preview and `main` deploys to production. `motion.djmiskey.com` is a DNS-only `CNAME` in Cloudflare (proxy off). `app/robots.ts` and `app/sitemap.ts` (generated from the registry) point crawlers at the custom domain.
- **Together** (`/gsap-three`, `/rive-three`): ScrollTrigger scrubs a timeline that tweens a plain object (camera position and target); `useFrame` copies it to the camera, so scrolling causes no React re-renders, and the view stays put with CSS `sticky`. Reduced motion swaps scrolling for buttons that jump between viewpoints. Rive becomes a texture by giving its player its own canvas and wrapping it in a `<canvasTexture>`; **Rive draws nothing into a canvas with a 0 × 0 on-screen box** (detached, or `@rive-app/react-canvas`'s component with container resizing off), so that canvas is attached to `<body>` at its real size, positioned off screen. Interactive Rive UI is a normal DOM overlay (`ThreeCanvas`'s `overlay` slot) pinned to a 3D point by `components/three/Anchor.tsx`, which projects the point each frame; drei's `<Html>` rendered nothing in this stack (React 19 / Next 16 / R3F 9), so the lab doesn't use it.
- **Performance** (`/performance`): Next.js prefetches the code of every page linked in the sidebar, and the Three.js and Rive pages imported those libraries directly, so **every page downloaded 598 KB of compressed JavaScript**, Three.js and Rive included. Each heavy demo is now its own chunk (`lazy.tsx`: `next/dynamic` with `ssr: false`, rendered by `components/Deferred.tsx`'s `WhenVisible` with a same-size `DemoPlaceholder`, so nothing shifts). Measured in headless Edge on the production build: home and GSAP pages 227 KB, Rive pages 292 KB + WASM, Three.js pages 470–540 KB. What's left everywhere is ~140 KB of Next.js/React and 79 KB of GSAP, kept eager on purpose. The page also tallies its own downloads live (`PerformanceObserver`), compares animating `transform` with `left/top`, and reports what it detects about the device.
- **CSP**: everything loads from this site: `.riv` files, models and textures go in `public/`. `connect-src` also allows `blob:`, because the glTF loader unpacks a model's embedded textures into blob URLs and fetches them. Script-src allows `'unsafe-inline'` because the pages are prerendered (see the Vercel lab's Security page for the nonce version).

## Roadmap

- [x] **Phase 1: Scaffold.** Registry, motion settings (reduced motion, off-screen pausing, FPS meter), one working page each: GSAP timelines, Rive playback, a Three.js scene
- [x] **Phase 2: GSAP.** ScrollTrigger (reveal, scrub, pin), SplitText (masked lines, characters, scroll-lit words), DrawSVG and MorphSVG, Flip (shuffle, filter, expand)
- [x] **Phase 3: Rive.** Data binding both ways (stocks dashboard), fit/alignment and `Fit.Layout` responsive artboards
- [x] **Phase 4: Three.js.** glTF model with animations (Fox), PBR materials with Lightformer environment lighting, a custom GLSL wave shader
- [x] **Phase 5: Together.** Scroll-driven 3D camera (GSAP × Three.js), Rive as a live texture and Rive UI pinned in 3D (Rive × Three.js)
- [x] **Phase 6: Performance.** Lazy-loaded Three.js and Rive (598 KB → 227 KB of JS on most pages), live download tally, transform vs layout frame budget, device detection
- [x] **Phase 7: Interaction.** Draggable + Inertia (throw, carousel, dial), Observer (one gesture, one slide), MotionPath (SVG path and curves through points), pointer effects (quickTo, magnetic buttons, tilt, gsap.matchMedia), Rive keyboard focus, key/text listeners and text input with semantics
- [x] **Phase 8: Advanced 3D.** Post-processing (bloom, depth of field, chromatic aberration, vignette, grain), instancing (50,000 cubes in one draw call vs separate meshes), Rapier physics (stacking, dropping, a kinematic pointer ball), WebGPURenderer with a TSL material
- [x] **Phase 9: Capstone.** Tower Toppler (`/game`): a three-level physics game. Three.js + Rapier world, GSAP camera swoop, split-text menus, score count-up and pops, Rive star rating, keyboard aiming
- [x] **Testing.** Playwright end-to-end suite in CI (144 tests: every page on desktop and phone, security headers, axe in light and dark, interactions). It found and fixed: `aria-label` on role-less elements (3D canvases, SplitText paragraphs), colour-only links, white-on-purple contrast in dark mode, the game not focusing its aiming layer, and `/gsap-scroll` overflowing phones
- [x] **Phase 10: Marble Maze.** A second capstone (`/marble`): tilt the board with the arrow keys/WASD, by dragging, or by tilting the phone (DeviceOrientation); three text-grid mazes with a breadth-first-search solvability test; Rive stars against par; an autopilot end-to-end test that finishes level 1
- [x] **Phase 11: Stacker.** A one-button tower game (`/stacker`) with no physics engine and no WebAssembly: pure slab-cutting rules in `stack.ts` (unit-tested), an orthographic camera lifted by GSAP, Perfect streaks that grow the slab back, and an autopilot end-to-end test that times its drops from the slab's mirrored offset
- [x] **Phase 12: Starfield Runner.** An endless asteroid run (`/runner`) with no physics engine and no WebAssembly: 90 colliding rocks plus 140 scenery rocks in two instanced meshes, recycled rather than re-created; a seeded random generator; distance checks for hits and near misses; boost with an energy bar; steering shared with Marble Maze (keys, drag, phone tilt)
- [x] **Phase 13: Leaderboards.** Live top-five boards on all four games, with idempotent, retried score submissions to the API lab
